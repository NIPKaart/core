# Collector and import integration contracts

Inventory for [#1272](https://github.com/NIPKaart/core/issues/1272), within [#1269](https://github.com/NIPKaart/core/issues/1269), reconciled after the 2026-10-13 retrospective (following [#1349](https://github.com/NIPKaart/core/issues/1349)) on 2026-10-13 against core [`26a2dfa`](https://github.com/NIPKaart/core/tree/26a2dfadbcf912c6447bc786b9b62adec47d87f6), disabled-parking [`b576534`](https://github.com/NIPKaart/disabled-parking/tree/b576534e621ff625bb8c250ca4e2bd907ab1e25a) and offstreet-parking [`0e2a8b8`](https://github.com/NIPKaart/offstreet-parking/tree/0e2a8b8a090d85d6bace98f1dbd548e5d4a561f6). This describes repository behavior and recorded integration evidence; production activation remains open in [#1303](https://github.com/NIPKaart/core/issues/1303).

[ADR 0002](../adr/0002-core-owns-publication-collectors-deliver-snapshots.md) owns the boundary: reusable packages retrieve source data; collectors select, normalize and deliver complete source-qualified snapshots; core validates, compares, reviews and publishes. Collectors are not public API clients and must not own core publication state or database writes. Both current collectors deliver through private R2 without core API or database credentials.

## Municipal contract ownership and compatibility

The [data delivery contract](data-import-contract.md) remains authoritative for field semantics, source mappings, limits, storage mechanics and recovery. Core owns acceptance and publication rules; `disabled-parking` owns producing compatible files and retaining pending bytes. Changes to `format`, dataset identity, selection or source-field meaning require a coordinated producer/consumer change and a reviewed mapping. Unknown formats are rejected; there is no automatic schema negotiation or public API compatibility promise. Existing dataset codes have no legacy aliases or automatic migration: handle registered datasets and pending files explicitly before switching them.

Both manual and machine intake converge on the same validator and staging logic. Delivery identity is scoped to the dataset and UUID, with SHA-256 of the exact bytes: identical retries reuse status, changed bytes conflict, and a new unchanged snapshot records receipt without duplicating parking records. Publication additionally checks retrieval ordering; equal timestamps with different delivery IDs conflict. Preserve original source claims and local corrections. Eindhoven is usable for intake and review under the [recorded source assessment](https://github.com/NIPKaart/disabled-parking/blob/b576534e621ff625bb8c250ca4e2bd907ab1e25a/docs/eindhoven-source-review.md) and [core contract](data-import-contract.md#eindhoven-source-review-integration). Public-domain reuse is accepted; `licence: null` means no verified SPDX identifier. Access and content currency remain unknown (`access_category: unknown`, `source_updated_at: null`). The assessment in [disabled-parking #821](https://github.com/NIPKaart/disabled-parking/issues/821) is complete, but it does not approve the source or publish records: existing source approval and record review still apply, without an additional publisher statement or dataset-specific runtime block.

Collector pending bytes are durable transport state; core alone retains import/review/publication state. “Stateless collector” in ADR 0002 does not mean discarding a pending delivery after an interrupted upload. See the [operational guide](collector-staging.md) for deployment and retention; repository implementation is separate from VM, credential and recovery acceptance.

## Discovery and source approval

Core lists dataset folders under `municipal/` and `offstreet/`. For an unknown folder, `DatasetDeliveryService` validates its newest object and `SourceRegistrar` creates a source awaiting approval. An invalid newest object registers nothing; discovery retries later. Countries and subdivisions must already exist. Core matches a municipality by official code, or links an existing uncoded municipality by name within its region; a missing municipality is created only when an administrator approves the source.

An administrator checks the source description, rights, selection, area and bounds once. Approval allows pending deliveries to enter intake and review; catalog publication remains an explicit separate decision. Rejection retains the source and receipts while processing is blocked. A changed approved description requires re-approval, except `expected_interval_hours`, which updates the cadence without re-approval. `config/dataset-deliveries.php` contains general enablement, lateness and observation freshness settings, not a per-dataset allowlist. No `nipkaart:register-dataset` command is needed. Lateness currently uses two expected delivery intervals; observation freshness uses ten minutes.

[ADR 0013](../adr/0013-discover-dataset-sources-from-deliveries-with-one-time-approval.md) still has decision status **proposed**. Discovery and approval are implemented; implementation alone does not change that status. Its original source-block catalog version was `nipkaart-offstreet-catalog-2`; the current catalog is `nipkaart-offstreet-catalog-3`, with capacity moved into separate observations (Amsterdam version 2, Hamburg version 3).

## Separate from web transport and public APIs

Under [ADR 0010](../adr/0010-separate-web-application-endpoints-from-public-api.md), `/map/...`, `/destinations/...`, `/profile/favorites/...` and `/admin/...` serve the first-party web application. Municipal upload/review and offstreet visibility controls belong here even when their inputs are import files or their responses are JSON. Their session/policy/CSRF behavior must not be reused as machine credentials. Collectors must not automate these routes or call discovery to synchronize imports.

`routes/api.php` currently declares no routes. There is no collector upload HTTP API and no external read API. [ADR 0011](../adr/0011-defer-external-api-and-bulk-data-access.md) defers external access; `/api/v1` remains reserved. A future public API needs its own explicitly accepted authentication, versioning, compatibility and data-exposure policy. Neither private R2 access nor successful import gives consumers a supported read/export interface, and the municipal format identifier does not reserve or define a public API version.

## Source identity reconciliation

For rotating, reused or missing upstream IDs, inspect existing reconciliation before rejecting the source or proposing another identity system. ADR 0003 owns provenance; the services below distinguish original source claims from retained application UUIDs. Municipal and offstreet policies remain separate. When a registration, format, identity policy or acceptance status changes, reconcile the affected rows and evidence links in this inventory in the same delivery or a linked documentation PR; keep operational acceptance separate from repository state.

### Municipal source IDs

[MunicipalIdentityService](../../app/Services/MunicipalIdentityService.php) and [MunicipalIdentityTest](../../tests/Feature/MunicipalIdentityTest.php), introduced in [#1377](https://github.com/NIPKaart/core/pull/1377), retain `ParkingMunicipal.id` across changed source IDs. A known source-ID binding requires unchanged original geometry; an unfamiliar ID can match only a unique exact combination of original geometry, street and access category. Nearby candidates within 20 metres are review suggestions, never automatic proximity matches. Changed/ambiguous identity evidence and duplicate assignments block publication until attributable administrator review. Decisions remain dataset-scoped and protected by stale tokens and locks; published imports retain immutable resolutions. Favorites and manual visibility survive, and source claims remain auditable. The municipal source-ID uniqueness constraint is replaced with an index; rollback to uniqueness can fail after reused IDs have been published.

### Offstreet source IDs

The offstreet implementation extends the source-qualified identity rule in ADR 0003: `(dataset_source, external_id)` identifies a source claim within a catalog version, while `ParkingOffstreet.id` identifies the facility across versions. This is an explicit extension for sources such as Hamburg whose publication IDs rotate; it does not merge municipal, community or offstreet persistence models. It is not production acceptance or automatic publication.

[OffstreetIdentityService](../../app/Services/OffstreetIdentityService.php) compares records within one dataset before the existing catalog diff. PostGIS measures source coordinates. A unique matching normalized display/source name and facility type within 30 metres can propose the existing facility automatically. Multiple nearby candidates, a reused ID with inconsistent evidence, changed names without enough corroboration, or two records targeting one facility block publication for identity review. Known source IDs still require consistent type, source-name evidence and a position within 200 metres. These conservative bounds are implementation policy, not a statistical probability. Original claims and measurement times remain unchanged.

The import review screen shows identity evidence and lets an administrator select a candidate or explicitly create a new identity, with a required reason. Dataset-scoped decisions retain actor, time and prior decision; the stale-review token and source/import locks protect concurrent changes. Publication stores an immutable `identity_resolution` on the import. Stable facility IDs preserve favorites, visibility and occupancy through re-numbering. The old `external_id` column retains the initial source ID as legacy provenance; the current claim is in `source_record`, and current/historical source links are in the import resolutions. That legacy column is no longer a unique facility key.

Only published complete catalogs advance `missing_since` and `consecutive_missing_deliveries`; a rejected/failed/partial delivery does not. A complete empty catalog is valid evidence of absence. Missing facilities are retained and not automatically hidden or deleted. A returning facility can resolve to its original ID and clears missing state. Publication still requires existing source approval and administrator review; recognizing a location does not publish a catalog automatically. Unknown new locations receive an ID only at publication.

### Versioned observations

Core additionally accepts `nipkaart-offstreet-observations-3`. It has the same measurement records/envelope as version 2, plus exactly one of:

- `identity_records`: a complete list of catalog-format claims from **the same upstream fetch** as the observations, with exactly the same source-ID set. Core applies the existing catalog record/bounds validator and resolves these against published facilities using only unique matching name, source name, type and a source position within 30 metres. It deliberately ignores numeric-ID continuity for this live matching. Ambiguous, unknown or duplicate targets receive no occupancy update. This does not stage an import, publish metadata or create a facility. The latest applied observation retains its identity claim privately as `observation_identity`.
- `catalog_delivery_id`: a UUID identifying the exact published catalog delivery whose source IDs the observations use. Core resolves against that import's immutable bindings, allowing precise historical/reused IDs. A pending/missing catalog retains the cursor for retry. A collector must preserve that identity context rather than point a new source generation at an unrelated catalog.

Hamburg's collector emits version 3 with same-fetch claims. One `park_and_ride_collection` request supplies the identity claims and measured values together; numeric source IDs are passed through unchanged. It does not use the previously drafted static UUID registry. Daily catalog delivery/review remains separate from frequent observations, avoiding a review queue entry per source-ID refresh. Amsterdam retains version 2. The generic `Collection.identity_records` capability is reusable by other collectors with rotating source IDs.

Version 2 remains supported for sources without observed ID changes. Once catalog publication establishes changed/reused IDs, core persistently requires identity context for that source and refuses ID-only observations. Unchanged/older measurement rules remain; unknown or ambiguous live records never create, publish or delete facilities. Catalog review is needed to adopt new/changed facility metadata or resolve ambiguous identities, not to acknowledge every occupancy poll.

### Validation and rollout

[OffstreetIdentityTest](../../tests/Feature/OffstreetIdentityTest.php) covers repeated renumbering, favorites/visibility/occupancy preservation, new/reused identities, ambiguous and duplicate matches, stale review decisions, authorization/dataset boundaries, empty/missing/returning catalogs, versioned observations and pending-reference retry. [OffstreetIdentityHamburgTest](../../tests/Feature/OffstreetIdentityHamburgTest.php) retains the two real 38-record snapshots from 11 October and verifies that explicit review of uncertain matches preserves every facility ID. The fixture records changes in source coordinates; it does not claim the operator has verified those identity decisions.

The additive migration retains existing records and IDs; historical imports without resolutions continue through the legacy lookup until a reviewed catalog establishes a resolution. Version 3 catalog references cannot use an old import without a resolution; same-fetch claims can still match its published facilities conservatively. No application/production database is migrated during local testing. After identities have diverged, rollback to the old unique `(dataset_source_id, external_id)` constraint can fail rather than deleting conflicting history; use a forward fix in a populated environment.
